## B-CI04-01 — Coolify build pada: `npm ci` EUSAGE (frontend)

**Ozbiljnost:** High (deploy potpuno blokiran) · **Status:** ✅ popravljeno

### Simptom (Coolify log, 2026-11-03 18:50)

```
#35 [frontend builder 4/6] RUN npm ci
npm error `npm ci` can only install packages when your package.json and
npm error package-lock.json ... are in sync.
npm error Missing: @testing-library/react@16.3.3 from lock file

npm error Missing: dompurify@3.4.17 from lock file
npm error Invalid: lock file's picomatch@4.0.5 does not satisfy picomatch@4.0.7
```

### Uzrok

Repo je **npm workspace monorepo** (`workspaces: backend, frontend, mobile`) sa
**tri** lock fajla: root, `backend/`, `frontend/`. Root lock je jedini koji se
stvarno održava (`npm install -w frontend` piše **samo** u root lock, čak i kad se
komanda pokrene iz `frontend/` — npm prepozna workspace root).

`frontend/Dockerfile` je gradio iz konteksta `./frontend` i radio
`COPY package.json package-lock.json` → koristio je **`frontend/package-lock.json`**,
koji je zarašao: nema `vitest`, `jsdom`, `@testing-library/*` (FE-02) ni `dompurify`
(FE-03). CI je bio zelen jer koristi **root** lock → build i deploy su se tiho
razilazili. Isti obrazac je već jednom pao u INF-01 (F-019) i tada je „popravljen”
skriptom `scripts/sync-docker-locks.sh`, koja ručno regeneriše standalone lockove —
što nije održivo (dva locka, dvije istine).

### Rješenje (jedan lock)

| Fajl | Promjena |
|------|----------|
| `docker-compose.yml` | `frontend.build.context: .` (root), `dockerfile: frontend/Dockerfile` |
| `frontend/Dockerfile` | `COPY package.json package-lock.json` + `backend/`, `frontend/`, `mobile/` `package.json` → `npm ci` (root lock) → `COPY frontend ./frontend` → `npm run build -w frontend`; runner kopira `frontend/dist` i `frontend/server` |

## B-CI04-02 — `P1001: Can't reach database server at localhost:5432` (env → kontejner)

**Ozbiljnost:** High (runtime blokada) · **Status:** ✅ dijagnostika + fail-fast

### Šta korisnik vidi

```
Please make sure your database server is running at `localhost:5432`.
◇ injected env (0) from ../.env
◇ injected env (0) from .env
Datasource "db": PostgreSQL database "fkgracanica", schema "public" at "localhost:5432"
Error: P1001: Can't reach database server at `localhost:5432`
```

### Analiza

| Trag | Značenje |
|------|----------|
| `injected env (0)` (dva puta) | `backend/prisma.config.ts` radi `dotenv` load za `../.env` i `.env`; **0 varijabli** = u slici nema `.env` fajla. To je ispravno (tajne ne idu u image) — znači Prisma radi **samo** sa procesnim env varijablama, bez fallbacka. |
| `localhost:5432` | Unutar Docker kontejnera `localhost` je **sam kontejner**, ne baza. Ili je u Coolify upisan `localhost` kao host, ili do kontejnera nije došao pravi `DATABASE_URL` pa je ostala vrijednost iz build-arg dummyja (`postgresql://build:build@localhost:5432/fkgracanica` — isti host i isto ime baze kao u logu). |
| „varijable su u Coolify" | Coolify za compose resurs piše varijable u `/artifacts/<uuid>/.env` i `docker compose` ih **interpolira** u `environment:` blok. Varijabla koja nije navedena u `environment:` nikad ne dođe do kontejnera; `${VAR}` bez vrijednosti postaje **prazan string** i greška se pojavi tek duboko u aplikaciji. |

### Primijenjeno

| Fajl | Promjena |
|------|----------|
| `docker-compose.yml` | `${VAR:?poruka}` za `DATABASE_URL`, `API_PUBLIC_URL`, `JWT_*_SECRET`, `ADMIN_EMAIL`, `ADMIN_PASSWORD` → deploy pada **odmah** sa imenom varijable koja fali; razumne defaultne vrijednosti za `PORT`, `DB_PROVIDER`, `SOCKET_IO_PATH`, `CORS_ORIGINS`, `JWT_*_EXPIRES`, `UPLOAD_PATH`, `INTERNAL_API_URL`, `REDIS_URL` |
| `scripts/diag-deploy.sh` | nova dijagnostika: env u kontejneru (maskirano), host/port iz `DATABASE_URL`, DNS unutar mreže, TCP provjera, zadnjih 20 linija loga |
| `docs/INFRASTRUCTURE.md` | sekcija „Env varijable na Coolify — zašto ne dođu do kontejnera" (tok `.env` → interpolacija → allowlista) |

### Šta korisnik treba provjeriti (van repoa)

1. Coolify → Application → Environment Variables: da `DATABASE_URL` **nije** `localhost`,
   nego host DB servisa na `db_net` ili javni host uz `sslmode=verify-full`.
2. Da backend kontejner stvarno vidi varijablu: `./scripts/diag-deploy.sh`.
3. Deploy sa grane koja sadrži ove izmjene (`main` do tada nema ni CI-04 fix builda).

### B-CI04-02 — dodatna analiza (2026-11-03, nakon korisnikovog env ispisa)

Korisnik je potvrdio da Coolify env **ima** `DATABASE_URL` sa hostom
`hgpchekxb6dutalsyctu42al:5432` (Coolify Postgres na `db_net`), a Prisma je javio
`at "localhost:5432"`. Dva eksperimenta (lokalno, isti Prisma/Konfiguracija) su
razdvojila moguće uzroke:

| Test | Komanda | Rezultat |
|------|---------|----------|
| 1 | `DATABASE_URL= npx prisma migrate status` | `PrismaConfigEnvError: Cannot resolve environment variable: DATABASE_URL` |
| 2 | `DATABASE_URL=postgresql://build:build@localhost:5432/fkgracanica npx prisma generate` | prolazi konfiguraciju, **ne** ispisuje `Datasource "db" … at localhost:5432` (generate se ne spaja) |

**Zaključak:** „prazna varijabla" **ne** daje `localhost:5432` — daje
`Cannot resolve environment variable`. Poruka `Datasource "db": … at "localhost:5432"`
nastaje **samo** kad proces stvarno ima `DATABASE_URL` sa `localhost`, a jedina
takva vrijednost u repou je bio **dummy build-arg** iz `backend/Dockerfile`
(`postgresql://build:build@localhost:5432/fkgracanica` — isti host, port, baza i
user). Dakle proces koji je pao nije imao Coolify env vrijednost, nego build-arg
default (build stage ili ručno pokrenut `prisma` bez env-a).

**Dodatno nađeno u korisnikovom env ispisu:** `DATABASE_URL` sadrži
`&amp;` (HTML-entitet) umjesto `&`:
`?sslmode=verify-full&amp;sslrootcert=/etc/ssl/certs/coolify-ca.crt`.
Posljedica: `sslrootcert` se **ne parsira** (postaje parametar `amp;sslrootcert`),
pa TLS/CA iz URL-a ne važi; aplikacija se dosad spajala jer je `NODE_EXTRA_CERTS`
pokrivao CA. To je latentni bug koji puca čim se `NODE_EXTRA_CERTS` promijeni.

**Primijenjeno (nastavak):**

| Fajl | Promjena |
|------|----------|
| `backend/Dockerfile` | dummy build-arg host `localhost` → **`build-arg-dummy.invalid`** (namjerno nevalidan): ako se ikad pojavi u grešci, odmah je jasno da je build-arg, a ne Coolify env. Isto u `docker-compose.yml` (`build.args`). |
| `scripts/diag-deploy.sh` | nova dva nalaza: detekcija `&amp;` u `DATABASE_URL` i detekcija `build-arg-dummy` hosta (uz postojeću detekciju `localhost`). |

**Šta korisnik treba provjeriti:**

1. U Coolify env vrijednost `DATABASE_URL` **prekucati** sa običnim `&` (ne `&amp;`).
2. `./scripts/diag-deploy.sh` → ako `DATABASE_URL` u kontejneru pokazuje
   `build-arg-dummy.invalid` ili `<NIJE POSTAVLJENA>`, varijabla ne prolazi u kontejner.
3. Host `hgpchekxb6dutalsyctu42al` mora biti **aktuelni** Postgres kontejner i backend
   mora biti na istoj mreži (`db_net`): `docker ps | grep -i postgres`,
   `docker exec <backend> getent hosts hgpchekxb6dutalsyctu42al`.
4. Deploy sa grane koja sadrži CI-04 izmjene (`main` ih još nema).

### B-CI04-02 — KONAČNI UZROK (2026-11-03, drugi Coolify log)

Nakon preimenovanja dummy hosta u `build-arg-dummy.invalid`, korisnikov backend je
javio:

```
Datasource "db": ... at "build-arg-dummy.invalid:5432"
Error: P1001: Can't reach database server at `build-arg-dummy.invalid:5432`
```

To je bio **odlučujući dokaz**: string `.invalid` postoji **samo** u `build.args`
(`docker-compose.yml`) i `ARG` (`backend/Dockerfile`) — nema ga nigdje u runtime
konfiguraciji. Dakle **Coolify (docker-compose pack) izvozi `build.args` u
okruženje i za `up`**, pa je build-arg `DATABASE_URL` pregazio pravu vrijednost iz
`environment:` bloka. Coolify UI je bio ispravan; problem je bio u tome što je
build-arg uopšte postojao. (Isto objašnjava i `--build-arg 'DATABASE_URL'` bez
vrijednosti u Coolify build komandi — vrijednost dolazi iz okruženja.)

**Rješenje — `DATABASE_URL` više ne postoji kao build-arg:**

| Fajl | Promjena |
|------|----------|
| `docker-compose.yml` | **uklonjen `DATABASE_URL` iz `build.args`** (komentar objašnjava zašto); runtime vrijednost samo iz `environment:` (fail-fast `${DATABASE_URL:?}`) |
| `backend/Dockerfile` | **uklonjen `ARG DATABASE_URL`** i `DATABASE_URL="$DATABASE_URL" npx prisma generate` → goli `npx prisma generate` |
| `backend/prisma.config.ts` | nema više `env('DATABASE_URL')` (bacao bi grešku bez varijable) → `process.env.DATABASE_URL ?? placeholder`; `prisma generate` ne otvara konekciju, pa placeholder smeta samo ako se pokuša spojiti |
| `backend/docker-entrypoint.sh` | **novi preflight** prije `prisma migrate deploy`: pada ako `DATABASE_URL` nema, pada ako je `build-arg-dummy`/`placeholder`, ispiše **maskiran** host (bez lozinke), pa pokrene migracije i `node dist/src/main.js` |
| `backend/Dockerfile` (CMD) | `CMD ["sh", "docker-entrypoint.sh"]` |
| `scripts/standards/docker-context.mjs` | novi guard: **`build.args`/`ARG` ne smiju sadržavati** `DATABASE_URL`, `REDIS_URL`, `*PASSWORD*`, `*SECRET*`, `*TOKEN*`, `*_KEY*` — hvata tačno ovaj tip greške prije deploya (dokazano lažnim `DATABASE_URL` build-argom: check pada) |
| `scripts/diag-deploy.sh` | nova provjera: **da li slika ima ugrađen `ENV DATABASE_URL`** (`docker image inspect`) — ako ima, build-arg/ENV je kriv |

**Verifikacija:**

| Provjera | Rezultat |
|----------|----------|
| `prisma validate` **bez** `DATABASE_URL` | ✅ config se učita (prije: `PrismaConfigEnvError`) — `prisma generate` u buildu više ne traži URL |
| `docker-entrypoint.sh` sa praznim env | ✅ `FATAL: DATABASE_URL nije postavljen …`, exit 1 |
| `docker-entrypoint.sh` sa dummy URL-om | ✅ `FATAL: … PLACEHOLDER iz builda` + maskiran ispis, exit 1 |
| `docker-entrypoint.sh` sa pravim URL-om | ✅ `[entrypoint] DATABASE_URL = postgresql://fkgracanica:***@hgpchek…` |
| `docker-context` guard | ✅ prolazi na repou; pada kad se doda `DATABASE_URL` u `build.args` |
| `npm run check:all` | ✅ 8/8 |

**Šta korisnik treba uraditi:** samo redeploy grane koja sadrži ovaj commit. U
Coolify env `DATABASE_URL` treba prekucati sa `&` umjesto `&amp;` (vidi gore).
Ako i dalje padne, `./scripts/diag-deploy.sh` će pokazati da li slika ima ugrađen
`DATABASE_URL` (tada je uzrok ENV u slici, ne env varijable).
